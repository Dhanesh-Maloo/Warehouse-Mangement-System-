NON-NEGOTIABLE CONVENTIONS (see CLAUDE.md) — apply these to any new module:
  - Every business table carries client_id — filter every query by it.
  - Money is BigInt paise, never float. ₹1 = 100 paise.
  - Timestamps are TIMESTAMPTZ, stored UTC, displayed in Asia/Kolkata.
  - events_ledger is append-only — corrections are new rows, never updates.
    (A Postgres trigger blocks UPDATE/DELETE on it at the DB level.)
  - Rate changes create a new RateCardItem version, never edit in place.
  - Naming: snake_case columns, camelCase Prisma fields, PascalCase models.

NOTES FOR ADDING A NEW CLIENT INVENTORY PROCESS
================================================================================
  - Asset (assets) is the spine everything else hangs off — clientId,
    currentStatus, currentLocationId, and the category/condition fields.
    A new process will almost certainly read/write this table.
  - AssetStatus is a single shared enum. If the new process needs a
    genuinely new state, that's a schema decision (migration + every place
    that switches on status), not just a new module.
  - RepairRequest and ResaleListing don't have Prisma relations on their
    clientId/assetId/createdByUserId fields — FK-shaped columns resolved
    manually in the service layer. Decide up front whether the new
    process should follow that pattern or use proper relations.
  - Every business table needs client_id, money is BigInt paise, timestamps
    are TIMESTAMPTZ/displayed IST, and events_ledger is append-only.
